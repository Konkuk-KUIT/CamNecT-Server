# Community 프론트엔드 연동 체크리스트

이 문서는 Community API 변경사항과 프론트엔드에서 반영해야 할 작업을 한 번에 전달하기 위한 문서다.

## 1. 게시글 목록은 서버 검색을 사용한다

게시글 검색을 현재 메모리에 로드된 `items`만 필터링하는 방식으로 구현하면 안 된다. 아직 내려받지 않은 다음 페이지의 게시글은 검색 대상에서 빠지기 때문이다.

검색 요청 예시:

```http
GET /api/community/posts?tab=ALL&sort=LATEST&keyword=스프링&size=20
```

프론트 구현 규칙:

- 검색어 입력은 250~400ms debounce한다.
- 검색어가 변경되면 진행 중인 이전 목록 요청을 취소한다.
- 검색어, 탭, 정렬, 태그 중 하나라도 변경되면 기존 `items`와 커서를 모두 초기화한다.
- 첫 검색 요청에는 커서를 보내지 않는다.
- 다음 페이지에도 첫 요청과 동일한 `tab`, `sort`, `tagId`, `keyword`를 보낸다.
- 검색 결과는 서버 응답으로 교체하고, 로컬 필터 결과를 최종 검색 결과로 사용하지 않는다.
- 검색어는 최대 100자다.

현재 검색은 제목과 본문의 부분 문자열 검색이며 검색 관련도순이 아니다. `sort`에 지정한 최신순·추천순·좋아요순·북마크순으로 정렬된다.

## 2. 게시글 커서 전달 규칙

응답 형식:

```json
{
  "items": [],
  "nextCursorId": 123,
  "nextCursorValue": 45,
  "hasNext": true
}
```

정렬별 다음 페이지 요청 규칙:

| 정렬 | 첫 페이지 | 다음 페이지 |
|---|---|---|
| `LATEST` | 커서 없음 | `cursorId=nextCursorId`만 전달 |
| `RECOMMENDED` | 커서 없음 | `cursorId`와 `cursorValue` 모두 전달 |
| `LIKE` | 커서 없음 | `cursorId`와 `cursorValue` 모두 전달 |
| `BOOKMARK` | 커서 없음 | `cursorId`와 `cursorValue` 모두 전달 |

주의사항:

- 추천·좋아요·북마크순에서 커서 하나만 보내면 `43040 INVALID_CURSOR`가 반환된다.
- 최신순에서 `cursorValue`를 보내도 `43040 INVALID_CURSOR`가 반환된다.
- `hasNext=false`이면 추가 요청을 보내지 않는다.
- 다음 요청에는 응답받은 커서 값을 변형하지 말고 그대로 전달한다.
- 정렬값은 실시간으로 바뀔 수 있으므로 무한 스크롤 목록은 `postId` 기준으로 중복 제거한다.
- 새로고침 또는 pull-to-refresh 시 커서를 제거하고 첫 페이지부터 다시 조회한다.

최신순 다음 페이지 예시:

```http
GET /api/community/posts?tab=ALL&sort=LATEST&size=20&cursorId=123
```

추천순 다음 페이지 예시:

```http
GET /api/community/posts?tab=ALL&sort=RECOMMENDED&size=20&cursorId=123&cursorValue=45
```

## 3. 댓글 커서 전달 규칙

댓글 목록은 루트 댓글 스레드 단위로 페이지를 가져온다.

첫 페이지:

```http
GET /api/community/posts/123/comments?size=20
```

응답 예시:

```json
{
  "items": [],
  "nextCursorId": 456,
  "hasNext": true
}
```

다음 페이지:

```http
GET /api/community/posts/123/comments?size=20&cursorId=456
```

프론트 구현 규칙:

- 첫 요청에는 `cursorId`를 보내지 않는다.
- `hasNext=true`일 때만 `nextCursorId`를 다음 요청의 `cursorId`로 보낸다.
- `size`는 응답 배열 길이가 아니라 한 번에 가져올 **루트 댓글 스레드 수**다.
- `items`에는 선택된 루트 댓글과 그 루트에 달린 대댓글이 함께 들어가므로 `items.length`는 `size`보다 클 수 있다.
- `parentCommentId=null`인 항목이 루트 댓글이며, 대댓글은 `parentCommentId`를 기준으로 묶는다.
- 다음 페이지 결과는 기존 스레드 뒤에 추가하고 `commentId` 기준으로 중복 제거한다.
- 게시글 화면을 새로 열거나 새로고침할 때 댓글 커서를 초기화한다.
- 삭제 댓글은 `author=null`이지만 신고·운영 이력 식별을 위해 `userId`는 유지될 수 있으므로 화면에는 작성자 프로필을 표시하지 않는다.
- 숨김·삭제 상태 게시글의 댓글 조회는 `43925`로 차단된다.

## 4. 게시글·댓글 입력 제한

### 게시글

- 제목: 공백만 입력 불가, 최대 200자, 줄바꿈 및 제어문자 불가
- 본문: 공백만 입력 불가, 최대 20,000자
- 태그: 최대 5개, 중복 불가
- 첨부파일: 최대 3개, 동일한 `fileKey` 중복 불가
- 첨부파일의 `width`와 `height`: 둘 다 보내거나 둘 다 생략
- 수정 요청: 최소 한 필드는 전달해야 함
- `anonymous`는 작성 요청에서만 사용한다. 게시글 수정 요청에는 보내지 않는다.
- 작성 이후 익명 여부 변경을 요청하면 `43930`이 반환된다.
- 수정 시 `tagIds: []`: 태그 전체 제거
- 수정 시 `attachments: []`: 첨부파일 전체 제거
- 수정 시 필드를 생략하거나 `null`: 해당 필드는 변경하지 않음

### 댓글

- 댓글/대댓글 본문: 공백만 입력 불가, 최대 5,000자
- `parentCommentId`: 전달 시 양수
- 삭제된 루트 댓글에는 새 대댓글 작성 가능
- 숨김 댓글에는 대댓글 작성 불가
- 채택된 댓글은 수정·삭제 불가

### ID와 페이지 크기

- 모든 `postId`, `commentId`, `attachmentId`, `tagId`, `cursorId`는 1 이상
- 게시글과 댓글의 `size`는 1~50
- `cursorValue`는 0 이상

### 첨부파일 업로드 발급 요청

- `contentType`: 필수
- `size`: 1 byte 이상이며 서버 설정 최대 크기 이하
- `originalFilename`: 최대 255자
- 파일명에는 `/`, `\\`, CR/LF 및 제어문자를 사용할 수 없음
- community 첨부파일의 허용 MIME 타입은 PDF, JPEG, PNG, WEBP

## 5. 익명 게시글 처리

- 익명 게시글 응답의 `author`는 `null`이다.
- `author`가 항상 존재한다고 가정하거나 강제 접근하면 안 된다.
- 익명 게시글은 팔로워 새 글 알림이 발송되지 않는다.
- 익명 질문의 채택 알림에는 질문 작성자 정보가 포함되지 않는다.
- 익명 여부는 작성 시 확정되며 게시글 수정 화면에서 변경할 수 없다.

## 6. 접근권한과 화면 노출 기준

- `accessType`은 게시글 자체의 접근 정책(`FREE`, `POINT_REQUIRED`)이다.
- `accessStatus`는 현재 사용자가 실제로 콘텐츠를 볼 수 있는지 나타낸다.
- 프론트의 잠금·노출 판단은 `accessType`이 아니라 `accessStatus`를 기준으로 한다.
- `GRANTED`: 본문 미리보기와 썸네일을 표시한다.
- `NEED_PURCHASE`: 구매 UI를 표시하고 보호된 본문·썸네일을 숨긴다.
- `INSUFFICIENT_POINTS`: 포인트 부족 UI를 표시하고 보호된 본문·썸네일을 숨긴다.
- `LOGIN_REQUIRED`: 로그인 유도 UI를 표시한다.

질문글·정보글의 포인트 적용 시점과 가격 정책은 아직 확정 전이므로 추후 서버와 프론트를 함께 조정한다.

## 7. 오류 처리

주요 Community 오류:

| 코드 | 의미 |
|---|---|
| `43040` | 커서 조합 오류 |
| `43041` | 검색어 형식 오류 |
| `43060` | 태그 ID 오류 |
| `43061` | 게시글 수정 요청에 변경할 필드가 없음 |
| `43912` | 공개 상태가 아닌 댓글 변경 시도 |
| `43925` | 공개 상태가 아닌 게시글 접근/변경 시도 |
| `43928` | 채택 댓글 수정·삭제 시도 |
| `43929` | 질문 작성자의 자기 댓글 채택 시도 |
| `43930` | 작성 이후 익명 여부 변경 시도 |
| `49021` | 첨부파일 메타데이터 오류 |
| `49022` | 첨부파일 키 중복 |

Bean Validation 실패는 공통 `40000 BAD_REQUEST`와 필드 오류 목록으로 반환된다.

```json
{
  "status": 400,
  "code": 40000,
  "message": "잘못된 요청입니다.",
  "errors": [
    {
      "field": "title",
      "message": "공백일 수 없습니다"
    }
  ]
}
```

- `errors[].field`는 `title`, `content`, `size`, `items[0].originalFilename` 같은 요청 필드 경로다.
- `$request`는 특정 필드 하나가 아니라 요청 객체 전체 조건이 잘못된 경우다.
- 서버는 보안상 거절된 실제 입력값을 오류 응답에 다시 포함하지 않는다.
- JSON 파싱 실패나 잘못된 enum 값처럼 필드 검증 이전에 실패한 요청은 기존 `ErrorResponse` 형식으로 내려올 수 있다.

## 8. 아직 확정되지 않은 후속 작업

다음 항목은 현재 프론트 구현을 확정하지 말고 별도 정책 결정 후 함께 변경한다.

- 질문글·정보글 포인트 및 유료 접근 정책
- 채택·판매 이후 게시글 수정 정책
- 하나의 루트 댓글에 대댓글이 매우 많을 때 대댓글 자체를 별도 페이지로 분리할지 여부
- 검색 관련도순 및 검색엔진 도입 여부
