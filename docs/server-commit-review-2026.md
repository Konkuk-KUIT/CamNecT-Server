# 2026년 서버 커밋 재검토 및 교정 기록

## 목적과 범위

- 대상: 2026년 3월 1일부터 `main`의 `6389184`까지 반영된 서버 변경
- 기준점: `dc8e37c` (2026년 3월 이전 마지막 커밋)
- 검토 방식: 병합 커밋만 보지 않고 원인 커밋과 후속 보완 커밋을 함께 추적한다.
- 수정 원칙: 프론트엔드 계약은 유지하고, 재현 가능한 오류나 무결성·보안 문제만 최소 범위로 교정한다.

- 커밋 규칙: `domain-corrections-<content>` 형식으로 교정 단위를 분리한다.

## 교정 기록

### `chat-corrections-secure-stomp-routing`

관련 변경 흐름:

- `46a179a` (#268): STOMP 구독 대상 검증 도입
- `c669762`, `a9d9bc5` (#273): SEND/SUBSCRIBE 프레임마다 계정·세션 재검증 도입
- `67bab81` (#275), `33fb918` (#283): Redis 토큰 폐기 및 다중 세션 검증 보완

발견한 문제:

1. 인증된 클라이언트의 `SEND` 목적지는 세션만 검사하고 경로를 검사하지 않았다. 따라서 애플리케이션 처리 경로가 아닌 단순 브로커 경로(`/sub/**`, `/queue/**`, `/room/**`)로 직접 메시지를 발행해 서버가 만든 것처럼 다른 구독자에게 전달할 수 있었다.
2. 알림 발행기는 `/user/queue/notifications`를 사용하지만 구독 허용 목록에 이 경로가 없어 정상적인 실시간 알림 구독도 거부됐다.

교정 내용:

- `SEND`는 실제 `ChatController`가 처리하는 메시지 전송과 방 퇴장 목적지만 허용한다.
- 기존 프론트엔드 호환성을 위해 설정에 공개된 `/pub`, `/send` 접두사는 모두 유지한다.
- 단순 브로커 목적지와 정의되지 않은 애플리케이션 목적지는 거부한다.
- `/user/queue/notifications` 구독을 허용한다.

계약 영향:

- 정상 경로인 `/pub|send/chat/message`, `/pub|send/chat/room/{양의 정수}/leave`는 그대로 동작한다.
- 정상 알림 구독이 복구된다.
- 컨트롤러를 우회하는 직접 브로커 발행만 새로 차단된다.

검증:

- `ChatStompInterceptorTest`: 9개 통과, 실패·오류·건너뜀 0개
- 정상 `/pub`·`/send` 목적지, 알림 구독, 브로커 직접 발행 및 미등록 경로 거부를 포함한다.

### `chat-corrections-preserve-sender-unread-count`

관련 변경 흐름:

- `8b88b99` (#268): 트랜잭션 커밋 후 채팅방·채팅 목록 실시간 갱신 도입

발견한 문제:

- 새 메시지를 보낸 사용자의 해당 채팅방 미읽음 수를 실제 상태와 무관하게 항상 `0`으로 발행했다. 사용자가 기존 수신 메시지를 읽음 처리하지 않은 채 메시지를 보내면 목록의 방별 미읽음 수만 거짓으로 0이 되고, 전체 미읽음 수와도 불일치한다.

교정 내용:

- 발신자도 수신자와 같은 저장소 쿼리로 해당 방에서 자신이 받았지만 읽지 않은 메시지 수를 계산한다.
- 실시간 목록 DTO의 발신자 `unreadCount`에 계산한 값을 사용한다.

계약 영향:

- DTO 구조와 STOMP 목적지는 바뀌지 않는다.
- 잘못 고정됐던 값만 데이터베이스의 실제 미읽음 상태와 일치하게 된다.

검증:

- `ChatRealtimeDeliveryServiceTest`: 4개 통과, 실패·오류·건너뜀 0개
- `ChatRealtimeDeliveryServiceTest`에서 발신자 방별 미읽음 수가 0이 아닌 상태를 구성하고, 발신자 목록 이벤트에 같은 값이 전달되는지 검증한다.

### `profile-corrections-complete-withdrawal-locking`

관련 변경 흐름:

- `189e453` (2026년 2월): 탈퇴 시 자격증·학력·경력 데이터를 일괄 삭제하는 흐름 도입
- `c74025f` (2026년 7월): 프로필 구성요소의 접근 검증 정리
- `28b6904` (#285): 탈퇴와 경력 변경에 공통 사용자 행 잠금을 도입하고 경력 행에도 별도 잠금을 추가

발견한 문제:

1. #285의 탈퇴 동시성 보완이 경력에만 적용되고 자격증·학력 생성·수정·삭제에는 적용되지 않았다. 탈퇴 트랜잭션이 자식 행을 삭제하고 사용자를 익명화한 뒤, 먼저 시작한 구성요소 변경이 뒤늦게 저장되어 탈퇴 사용자에게 데이터가 다시 생길 수 있었다.
2. 경력 변경은 사용자 행을 먼저 잠가 같은 사용자의 모든 프로필 변경을 이미 직렬화하면서 경력 행까지 다시 잠갔다. 탈퇴 경쟁 방지에는 중복 잠금과 별도 저장소 메서드가 필요하지 않았다.

교정 내용:

- 자격증·학력의 모든 변경 작업이 탈퇴와 같은 사용자 행 잠금을 먼저 사용하도록 통일한다.
- 조회 작업은 기존처럼 잠금 없이 유지한다.
- 경력은 사용자 행 잠금만 유지하고 중복된 경력 행 잠금 쿼리와 그 잠금 계약 테스트를 제거한다.

계약 영향:

- HTTP 요청·응답 구조는 바뀌지 않는다.
- 같은 사용자의 탈퇴와 프로필 구성요소 변경만 직렬화되며, 서로 다른 사용자의 변경은 서로 막지 않는다.

검증:

- `CertificateServiceLockingTest`, `EducationServiceLockingTest`, `ExperienceServiceLockingTest`, `DeletionLockContractTest`: 총 6개 통과, 실패·오류·건너뜀 0개
- 자격증·학력의 생성·수정·삭제가 모두 사용자 행 잠금을 사용하고, 경력은 사용자 잠금 뒤 일반 조회로 처리되는 순서를 검증한다.

### `notification-corrections-block-withdrawn-device-registration`

관련 변경 흐름:

- `fd04690`, `546354d`: 사용자별 푸시 기기 등록·갱신 흐름 도입 및 보완
- `28b6904` (#285): 탈퇴와 연관 데이터 변경에 사용자 행 잠금 규약 도입
- `81acd66` (#284): 푸시 알림 흐름 보완

발견한 문제:

- 푸시 기기 등록은 사용자 행을 잠근 뒤 정지 상태만 거부했다. 요청 인증 직후 탈퇴가 먼저 완료되면, 대기하던 등록 트랜잭션이 탈퇴 상태를 읽고도 새 기기를 `enabled=true`로 저장할 수 있었다.

교정 내용:

- 사용자 행 잠금 뒤 상태가 `WITHDRAWN`이면 저장소 변경 전에 기존 `USER_WITHDRAWN` 오류로 중단한다.
- 승인 대기 사용자의 기존 푸시 등록 계약은 유지한다.

계약 영향:

- 정상 사용자와 승인 대기 사용자의 요청·응답은 바뀌지 않는다.
- 탈퇴가 먼저 확정된 요청만 거부된다.

검증:

- `PushDeviceServiceTest`: 6개 통과, 실패·오류·건너뜀 0개
- `PushDeviceServiceTest`에서 잠금 뒤 탈퇴 상태를 반환하고, 기기 비활성화·저장 로직에 진입하지 않는지 검증한다.
