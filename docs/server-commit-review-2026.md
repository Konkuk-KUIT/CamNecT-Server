발견한 문제:

1. 인증된 클라이언트의 `SEND` 목적지는 세션만 검사하고 경로를 검사하지 않았다. 따라서 애플리케이션 처리 경로가 아닌 단순 브로커 경로(`/sub/**`, `/queue/**`, `/room/**`)로 직접 메시지를 발행해 서버가 만든 것처럼 다른 구독자에게 전달할 수 있었다.
2. 알림 발행기는 `/user/queue/notifications`를 사용하지만 구독 허용 목록에 이 경로가 없어 정상적인 실시간 알림 구독도 거부됐다.

교정 내용:

- `SEND`는 실제 `ChatController`가 처리하는 메시지 전송과 방 퇴장 목적지만 허용한다.
- 기존 프론트엔드 호환성을 위해 설정에 공개된 `/pub`, `/send` 접두사는 모두 유지한다.
- 단순 브로커 목적지와 정의되지 않은 애플리케이션 목적지는 거부한다.
- `/user/queue/notifications` 구독을 허용한다.

계약 영향:

- 정상 경로인 `/pub|send/chat/message`, `/pub|send/chat/room/{양의 정수}/leave`는 그대로 동작한다.
- 정상 알림 구독이 복구된다.
- 컨트롤러를 우회하는 직접 브로커 발행만 새로 차단된다.

검증:

- `ChatStompInterceptorTest`: 9개 통과, 실패·오류·건너뜀 0개

- 경력은 사용자 행 잠금만 유지하고 중복된 경력 행 잠금 쿼리와 그 잠금 계약 테스트를 제거한다.

계약 영향:

- 같은 사용자의 탈퇴와 프로필 구성요소 변경만 직렬화되며, 서로 다른 사용자의 변경은 서로 막지 않는다.

검증:

### `verification-corrections-lock-document-user-state`

관련 변경 흐름:

- `935963e`, `2694293`: 문서 인증의 상태·오류 처리와 관리자 심사 잠금 보완
- `28b6904` (#285): 탈퇴와 사용자 연관 변경의 공통 사용자 행 잠금 규약 도입

발견한 문제:

1. 문서 업로드 URL 발급과 제출은 사용자 행을 잠근 뒤에도 존재 여부만 확인했다. 이미 승인된 사용자도 새 신분증 업로드와 `PENDING` 제출을 만들 수 있지만 관리자 승인은 `ADMIN_PENDING`만 허용하므로, 처리할 수 없는 제출과 저장 파일이 남았다.
2. 탈퇴가 먼저 완료돼도 사용자 행은 삭제되지 않으므로 같은 경로로 민감한 문서를 다시 올릴 수 있었다.
3. 관리자 심사는 제출 행만 잠그고 사용자를 비잠금 조회했다. 심사 도중 탈퇴와 경합하면 이전 상태를 기준으로 심사를 계속해 실패·롤백되거나 일관되지 않은 심사 결과를 만들 수 있었다.

교정 내용:

- 업로드 URL 발급과 제출은 기존 `잠금 쿼리 + 존재 확인 쿼리`를 사용자 잠금 조회 1회로 줄인다.
- 잠금 뒤 `ADMIN_PENDING`만 문서 업로드·제출을 허용하고 정지·탈퇴는 각 기존 상태 오류로 거부한다.
- 관리자 심사는 승인·반려 모두 최신 사용자 상태를 잠금 조회하고, 계정 상태를 바꾸는 승인은 `ADMIN_PENDING`인지 다시 확인한다. 반려는 기존처럼 과거 대기 건을 정리할 수 있다.
- 허용되지 않은 제출 상태는 전용 오류 `42931 DOCUMENT_SUBMISSION_NOT_ALLOWED`로 구분하고 OpenAPI 응답 문서에 반영한다.

계약 영향:

- 승인 대기 사용자의 정상 업로드·제출·심사 계약은 유지된다.
- 이미 승인·정지·탈퇴한 사용자의 새 문서 생성과 심사만 차단된다.

검증:

- `DocumentVerificationStateLockingTest` 2개와 `AdminDocumentVerificationLockingTest` 2개: 총 4개 통과, 실패·오류·건너뜀 0개
- 최신 사용자 상태를 잠근 뒤 저장소·업로드 작업 전에 거부하는지와, 탈퇴 사용자의 승인 심사가 진행되지 않는지 검증한다.

### `storage-corrections-expire-only-stale-upload-tickets`

관련 변경 흐름:

- `6c23524`, `d336600`: 업로드 티켓의 PENDING 만료 처리와 다건 발급 흐름 도입
- `4d5c661` (#278): 신고 증거의 다건 업로드 경로 도입

발견한 문제:

- 새 업로드 URL을 발급할 때 사용자·용도가 같은 `PENDING` 티켓을 만료 시각과 무관하게 모두 `EXPIRED`로 바꿨다. 아직 유효한 제한 수만큼 URL을 받은 직후 다시 요청하면 기존 티켓이 강제로 제한 집계에서 빠져 발급 한도를 반복 우회할 수 있었다.
- 기존 presigned URL은 서명 만료 전까지 실제 업로드에 사용할 수 있어, DB 제한 우회와 임시 저장 객체 누적이 함께 발생할 수 있었다.

교정 내용:

- 일괄 만료 쿼리에 `expiresAt <= now` 조건을 추가한다.
- 서비스에서 주입된 `Clock`으로 시각을 한 번 계산해 만료 처리와 활성 티켓 집계에 같은 경계값을 사용한다.
- 업로드 티켓 저장소를 직접 쓰는 활동 첨부 경로도 이미 계산한 같은 `now`를 전달한다.
